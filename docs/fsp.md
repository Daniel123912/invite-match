# Схема интеграции с FSP / FSP ID

## Текущее состояние (хакатон)

Боевого API и Keycloak-доступов нет. Реализована **имитация**:

1. Кандидат указывает `fsp_id` в настройках (например `FSP-1001`).
2. Backend дергает заглушку `GET /api/fsp/{fsp_id}/achievements`.
3. По ответу выставляются `has_fsp_history` и `fsp_score`.
4. Баллы участвуют только в **ранжировании**, не в присвоении грейда.

Демо-ID из seed: `FSP-1001`, `FSP-1002`, `FSP-2001`. Пустой / неизвестный ID → «истории нет».

## Целевая схема после хакатона

```
┌──────────┐   OIDC    ┌─────────────┐   API achievements   ┌──────────┐
│ FSP Match│ ────────► │ Keycloak /  │ ───────────────────► │ FSP API  │
│ (наш BE) │ ◄──────── │ FSP ID SSO  │ ◄─────────────────── │ registry │
└──────────┘   tokens  └─────────────┘   места, разряды     └──────────┘
```

| Шаг | Описание |
|-----|----------|
| 1 | Вход через FSP ID (OIDC), email+пароль остаётся fallback |
| 2 | По согласию пользователя подтягиваем участия, места, разряды |
| 3 | Нормализуем в `fsp_score` (свежесть результата можно усилить позже) |
| 4 | Периодический refresh профиля; отзыв согласия отключает публикацию |

## Что учитываем в скоре (логика заглушки)

- Число соревнований и результативность (победитель / призёр vs участие).
- Не ранжируем дисциплины («чемпионат выше хакатона») — по рекомендации Q&A.
- Не пытаемся выделить вклад в командный онлайн-хакатон.
