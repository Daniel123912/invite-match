# Процедура валидации и результаты

Команда сама задаёт эталонные пары и проверяет, что тест и подбор ведут себя ожидаемо. Жюри дополнительно проверит на своём закрытом наборе.

## Что проверяем

1. **Разделяющая сила теста** — Junior / Middle / Senior не получают одинаковый исход на «сильном» и «слабом» профиле ответов.
2. **Категоризация** — в подборку категории попадает только кандидат с релевантной спец. и выбранным/подтверждённым грейдом.
3. **Ранжирование** — при равном тесте выше тот, у кого больше FSP; без FSP человек не выпадает, а идёт ниже при прочих равных.
4. **Антислив** — две подряд попытки (или два кандидата) на одну категорию получают разные `variant_group` с заметной частотой (A vs B).
5. **Контакты** — до accept в ответе API работодателя нет phone/email кандидата.

## Эталонный набор (сиды)

| Вакансия / потребность | Ожидаемый топ | Почему |
|------------------------|---------------|--------|
| Backend × Middle, стек Python | `candidate@demo.ru`, `cand2@demo.ru` | Подтверждённый Backend Middle; у обоих есть FSP |
| Backend × Middle, без FSP-фильтра | `cand3@demo.ru` в выдаче | Высокий тест, `has_fsp_history=false`, reason про отсутствие ФСП |
| Frontend × Junior | `cand4@demo.ru`, `cand5@demo.ru` | Категория Frontend Junior |
| Новый `new@demo.ru` до теста | Не в топе категории | Нет подтверждённой категории |

Демо-пароль для всех: `demo1234`.

## Автотесты

```bash
cd backend
pytest -q
```

Покрывают сквозной flow (регистрация/confirm → опрос → тест → match → invite → accept → контакты), кулдаун грейда и отзыв согласия 152-ФЗ.

## Ручной чеклист (5 минут)

1. Войти `new@demo.ru` → опрос Backend/Middle → тест → категория.
2. Войти `employer@demo.ru` → подборка Backend Middle → увидеть `reason` → пригласить с зарплатой.
3. Снова кандидат → принять → у работодателя открылись контакты.
4. Опрос DevOps → тест стартует без 404 (категории сидятся).
